## Emulator choice: pcs2x6 vs Play!
- **pcs2x6** (PCSX2 fork): FAST — the only viable-perf option on the Deck. Needs COH-H 246/256 BIOS + per-game dongle + proverb + CHD + `.acgame`. Single-gun aim.
- **Play!** (`org.purei.Play` flatpak): boots namco2x6 natively (arcadedefs + zip + chd, **no BIOS**, HLE) but **atrociously slow** on the Deck for 246/256 ("WIP, needs a high-performance system"). Single-gun. Last resort only. Format: `arcadedefs/*.arcadedef` (JSON) + MAME-name `.zip` (raw `.ic002` chips) + `<id>/<disc>.chd`; arcaderoms at `~/.var/app/org.purei.Play/config/Play Data Files/arcaderoms/`.

## ⚠️ THE BOOT GOTCHA: dongle must be `.ps2`, not `.bin`
pcs2x6's `pcsx2/SIO/Memcard/MemoryCardFile.cpp` runs ANY memcard filename ending in `.bin`/`.mc2` through `ConvertNoECCtoRAW()` — it ADDS a 16-byte ECC per 512 bytes, assuming a no-ECC input. But the Namco dongle is **already** an 8 MB+ECC PS2 card (8,650,752 bytes; superblock "Sony PS2 Memory Card Format 1.2.0.0"; `CF_USE_ECC`). So ECC is added TWICE → the FAT/root is scrambled → `proverb` can't `fioOpen("mc0:<BOOTPROG>")` → returns -1 → the System 246 BIOS shows **"Boot program error / boot file not exist"** (falls through to `rom0:OSDSYS`). Page 0 (superblock) survives, so the log still says "Formatted" — misleading. A **`.ps2`** filename takes the direct-open branch (no conversion), which is exactly what an already-ECC card needs. The official pcs2x6 tutorial literally says "rename the `.bin` dongle to `.ps2`" — easy to miss.

## Canonical per-game recipe (5 pieces)
1. **BIOS** (once): arcade **COH-H System 246/256** — `r27v1602f.7d` (246) / `r27v1602f.8g` (256). Into pcs2x6's `bios/`. NOT a retail PS2 BIOS. Log: "COH-H System 246 Rack C …".
2. **Dongle**: the per-game security memcard as a **`.ps2`** (8,650,752-byte ECC card; FAT root holds `boot.bin`, `ACLOAD`, the BOOTPROG ELF e.g. `VPNGAME`/`TC3LOAD`). Into pcs2x6's **`memcards/`**. The curated dongle dump IS the right artifact — just name it `.ps2`. Unique per game.
3. **proverb.elf** (per-game bootloader): from the Proverb pack (github PS2Homebrew-arcade/proverb v1.0.3 `bin/NMxxxxx/proverb.elf`) or the v0.0.10 `system2x6_template_gamelibrary.7z`. Compiled with `BOOT_PATH=<bootprog>` baked in (per-game md5s differ); does `fioOpen("mc0:"+BOOT_PATH)` from the dongle. **Cannot be shared** between games. (`elf=` may alternatively be the decrypted dongle `boot.bin` → boots `mc0:ACLOAD` → AC env → game; the more robust native route.)
4. **Disc CHD**: DVD → `chdman createdvd -i x.iso -o x.chd -hs 2048`. CD → must be **MODE2_RAW** (pcs2x6's CD-CHD reader only matches literal `MODE2_RAW`/`MODE1_RAW`; `MODE2_FORM1`/`MODE1`/plain `MODE2` read garbage → boot fails). Pre-made CD CHD from a proper source is easiest. ⚠️ Some archive `.iso.gz` dumps have an **8-byte prefix defect** (PVD at offset 32777 not 32769; `file` says "data"); strip the first 8 bytes + pad 8 to re-align before converting.
5. **`.acgame`** (what gets launched):
   ```
   [game]
   name=Vampire Night
   gameid=NM00003
   platform=246
   [data]
   subdir=NM00003
   elf=proverb.elf
   dongle=vnight-vpn3verb.ps2
   mediasrc=NM00003.chd
   media=CD
   jvsmode=lightgun
   ```
   `gameid` can be legitimately DUPLICATED (NM00003 = Vampire Night AND Technic Beat — Namco recycled the dongle; both share bootprog VPNGAME). Launch: `pcsx2x6.AppImage -portable -batch -fullscreen -- <path>.acgame`. Search: dongle in `memcards/`; elf+media+sram in the `.acgame`'s `subdir`.

## Gun buttons (GunCon2, USB1)
**TC4 (NM00032) TEST-MENU navigation** (✅ on-device 2026-06-25): set `[JVS] TestMode = true` to enter. Navigate with `[JVS] P1_Up` / `P1_Down` (JVS UP 0x20 / DOWN 0x10; bind to the gun d-pad's keys or keyboard arrows). **ENTER/confirm = `[JVS] P1_Button1`** (JVS_BTN_1 = 0x02), NOT `P1_Start` (0x80) which was a wrong guess. The guncon2 D-pad is NOT forwarded to JVS so `guncon2_Up/Down` are dead in a JVS game, and the gun TRIGGER does NOT navigate (that is Vampire Night, where TC4's trigger is JVS_BTN_LEFT 0x08). Exit a sub-screen: select its on-screen EXIT line + Button1 (✅ confirmed on-device 2026-06-25); the manual's Up+Enter (Up+Button1) combo is an untested alternative. Leave test mode by setting `TestMode=false`. ⚠️ Edit `[JVS]` ONLY with pcsx2x6 CLOSED: it rewrites the ini on exit and silently drops bindings added while running (this is why a `P1_Start` edit "vanished" mid-debug). JVS bind names are in ACJV.cpp `s_jvs_p1_button_bindings` (P1_Up/Down/Left/Right, P1_Button1..6, P1_Start, P1_Service); bits in ACJV.h.

USB1/USB2 auto-set to `guncon2`. The S246 game reads the **GunCon2 device's** buttons (not the PS2 pad), and they're **unbound by default**. Bindable keys (guncon2.cpp): `Trigger`(p1/p2 trigger), `A`(foot pedal/reload), `Start`, `Select`(coins), `Up/Down/Left/Right`, `RelativeLeft/Right/Up/Down`(aim — NOT used for S246). Bind `Trigger` to the Sinden's mouse button (`Pointer-0/LeftButton`). `[JVS] TestMode=false` (TestMode is the "test menu" DIP — leave OFF or the game auto-boots the arcade I/O-TEST menu; set it ON only to calibrate the gun, then back OFF). `[JVS] SuppressDaemon=true` is a SEPARATE boot workaround — it suppresses the DAEMON module's security thread to dodge a dongle-open race (`IopBios.cpp`, in-emulator label "Suppress DAEMON security thread"); it has nothing to do with the test menu, defaults ON, and should stay ON.

## JVS lightgun protocol — gun position & 2-player I/O (cached 2026-06-23)
Source of truth for the I/O layer (ACJV.cpp). **MAME `src/mame/namco/namcops2.cpp` is a NON-WORKING STUB** (empty INPUT_PORTS, all games MACHINE_NOT_WORKING) → it does NOT emulate JVS guns and is **useless as a protocol reference**. Use these instead:
- **READ_INP_SCREENPOS (cmd 0x25)** — JAMMA Video Standard 3rd ed. §4.3.15 (http://daifukkat.su/files/jvs_wip.pdf): the request's `channel` byte is a **1-INDEXED SELECTOR**, and the reply is **EXACTLY ONE X/Y pair**: `[status=01][X_MSB][X_LSB][Y_MSB][Y_LSB]` (X first, big-endian per axis). It is NOT a count of N pairs (unlike ANLINP 0x22 / COININP 0x21 / ROTINP 0x23 whose byte1 IS a count). A board advertises its gun count via FEATCHK (0x14) function code **0x06** (Prm3 = channels); the game then reads each gun by index: **channel 1 → gun1/P1, channel 2 → gun2/P2**, as SEPARATE 0x25 calls. Off-screen = (0,0) coords (no separate "sensor" bit on real HW). Corroborated: YAJVSEmu `JvsIo.cpp`, TeensyJVS `jvs.ino` (reply = cmd+1 param → 4 position bytes). ⚠️ Emitting N pairs for channel=N over-runs the frame by 4·(N-1) bytes and **desyncs the JVS reply → P2 dead** (this was our bug through Build A).
- **READ_INP_SWITCH (cmd 0x20)** — request = playerCount + bytesPerPlayer; reply = system byte then per-player switch words from a SINGLE node. Bit layout (Nintendont JVSIO.c, YAJVSEmu): byte0 = START 0x80, SERVICE 0x40, UP 0x20, DOWN 0x10, LEFT 0x08, RIGHT 0x04, PUSH1 0x02, PUSH2 0x01; byte1 = PUSH3..10. **P2's trigger/start live in word1 (player-2's word), SAME bits as P1 in word0 — NOT a spare bit in word0.** On-device VPN reads switches with **playerCount=1** (only word0), so P2 buttons via word1 require the game to issue a 2-player switch read.
- **2-gun board = ONE JVS node**, not two. Real VPN I/O = V221 MIU/TMIU (rebranded; CCD-camera + IR gun, "not optical" per Arcade Otaku), reporting PLAYERS 2 / COINS 2 / GUN_CHANNELS 2. Refs: OpenJVS IO descriptors `namco-jyu` (2-gun) vs `namco-v185`/TSS (1-gun, TC2); https://wiki.arcadeotaku.com/w/Namco_System_246/256 ; https://www.arcade-projects.com/threads/system-246-256-i-o-board-gun-compatibility.1556/ . KLOV confirms VPN = 2 simultaneous players (https://www.arcade-museum.com/Videogame/vampire-night). ⚠️ **The conclusion drawn here at the time — "2-gun VPN is real & I/O-fixable, not game-limited" — was later OVERTURNED on-device (2026-06-24).** VPN is real 2-gun in the arcade, but its gun board is the exotic undocumented V221 MIU/TMIU (CCD/IR), NOT this standard JVS screenpos+switch model. Feeding the spec-correct JVS bits (incl. the disasm-derived word0 bit 0x10) did NOT make gun-2 fire in gameplay. See the CLOSED/BANKED verdict in the "2-player dual-Sinden" section above.
- pcsx2x6 has TWO gun input paths: JVS (ACJV: screenpos position + switch trigger via SetButtonState) AND USB GunCon2 report (`guncon2_handle_data` ep1 IN → `out.buttons = ~button_state`). Which one VPN reads P2's trigger from (USB2 vs JVS word1) was UNRESOLVED as of Build B → USBRD probe added to settle it.

## ✅ RESOLVED 2026-06-24 — live-RAM reverse-engineering of VPNGAME (IOP + EE memory dumps)
RE'd a live capture (P2 trigger physically held; JVS `word0 = 0x6200`) of the running game's IOP RAM (8MB, MIPS R3000, `n246Jvio` driver) and EE RAM (128MB, R5900). Method: capstone MIPS32-LE disasm. This settles the P2-trigger question definitively — **it is a SWITCH-WORD BIT-LAYOUT mismatch, not USB-vs-JVS and not "word1 dropped".**

**The live per-frame JVS poll** (byte-identical in IOP send buf @ file 0x86a22 and EE SIF build buf @ 0x20b6e2): `E0 01 0D 20 01 02 21 02 25 01 25 02 32 01 60 D4` = `READ_SWITCH players=1 bytes=2` + `READ_COIN 2` + `READ_SCREENPOS ch1` + `READ_SCREENPOS ch2` + `GP_OUT`. So the game reads **ONE switch word0** (never word1; NO `players=2` switch frame exists anywhere) but two gun positions. Board ID reply (IOP 0x86922 / EE 0x20b5e2) = `namco ltd.;Sys246gun;VerA;JPN`.

**The IOP is INNOCENT** — `n246Jvio` copies the 16-bit switch word VERBATIM to the EE via SIF DMA (memcpy 0x143370 / decode 0x155608; no mask/shift/repack). word0 bit 0x2000 reaches the EE intact.

**THE BUG — the EE switch demux `0x1a0f54` (the game's ONE switch processor):** gated by board-mode byte `0x42390b` (live = **0** → single-board path). It **bit-splits the single word0 by POSITION** into normalized per-player words (verified disasm):
  - **P1 trigger ← word0 bit 0x80**, P1 sensor ← bit 0x100  (→ 0x3cc7b0, normalized to 0x8000/0x200)
  - **P2 trigger ← word0 bit 0x10**, P2 sensor ← bit 0x20    (→ 0x3cc7c0, normalized to 0x8000/0x200)
  - status word 0x3cc7d0 = `word0 & 0x7208` (preserves native 0x2000/0x4000/0x200)
The emulator's ACJV packs **P2 trigger at word0 bit 0x2000** (and P1 trig 0x0001, P1 sens 0x0200, P2 sens 0x4000). With board-byte=0, the active demux reads **P2 trigger from bit 0x10 — which the emulator leaves CLEAR — so the normalized P2 trigger = 0, gun-2 is dead.** (The multi-board path 0x1a0fb8, board-byte==2, reads word0 @+0x12 AND word1 @+0x1a — needs a `players=2` reply the game never requests, so it's inactive.)

**Why I/O-TEST shows P2 trigger but gameplay doesn't:** the test/menu cursor code (`SwitchMgrClass`, e.g. 0x1b8b54) reads the raw/status word (native bit 0x2000 preserved by the 0x7208 mask) directly; the gameplay `GunMgrClass` gun handler (0x178970, per gun object via the `$gp-0x74f4` list, next-ptr +0xf0) consumes a per-gun reconstructed switch word at obj+0x3c (trigger normalized to bit 0x2000). The two consumers source the bits differently → test works, gameplay doesn't.

**THE ATTEMPTED FIX (emulator ACJV side) — ⚠️ TESTED ON-DEVICE, DID NOT WORK → 2P is CLOSED/BANKED (see the "2-player dual-Sinden" section above):** this RE pointed at a word0 bit-layout fix, and we built an ini override to try it (`P2TriggerBit=0x0010` + `P2SensorBit=0x0020`), but on-device gun-2 STILL did not fire in gameplay. The real wall turned out to be VPN's exotic undocumented V221 MIU/CCD/IR gun board, which no emulator reproduces. The disasm below is kept as accurate RE of the standard path, NOT as a shippable fix. For the record, the single-board path expects, in word0: **P1 trig = bit 0x80, P1 sensor = bit 0x100, P2 trig = bit 0x10, P2 sensor = bit 0x20** (JVS byte0: START 0x80=P1trig? no — these are the literal word0 bit values the demux extracts). I.e. make ACJV's READ_SWITCH word0 set P2 trigger at bit 0x0010 and P2 sensor at 0x0020 (and P1 trig 0x0080 / sensor 0x0100), OR drive the multi-board path (set board-mode byte → 2 and emit a `players=2` reply with word1 carrying P2). Caveat: the exact per-frame writer of the gameplay gun object's obj+0x3c (native 0x2000 vs the 0x10-normalized word) was not isolated statically (offset 0x3c is aliased int-switch vs float-coord; heavy R5900-MMI obfuscation) — confirm with a live watchpoint on word0 (reply struct +0x12) and obj+0x3c (handler 0x178a34) with P2 trigger held, one frame. Key EE addrs: demux 0x1a0f54 (split) / 0x1a0fb8 (multi-board) ; board byte 0x42390b ; gun handler 0x178970 (trig 0x2000 @0x178a38, sens 0x4000 @0x178a40) ; GunMgr walk 0x174d30 ; gun factory 0x173ed4. NB: firmware symbol names are `n246Jvio*` (IOP) and `GunMgrClass`/`SwitchMgrClass` (EE) — the "GetSwTrigger/GetJammaF/NamcoGun" names are emulator-side labels, absent from the binaries.

## Retail GunCon2 split: -datapath / -portable precedence + memcard (2026-07-01)
Source: fork code /home/deck/pcsx2x6-src/pcsx2/Pcsx2Config.cpp (EmuFolders::ShouldUsePortableMode +
SetDataDirectory) + pcsx2-qt/QtHost.cpp arg parsing; verified reading the source 2026-07-01.
- Data-root precedence (highest first): (1) `portable.ini`/`portable.txt` next to the AppImage
  (the $APPIMAGE dir, NOT the temp mount) OR the `-portable` flag => PORTABLE: data root =
  `<appimage_dir>/PCSX2x6`, and `-datapath` is IGNORED (QtHost help: "-portable ... Overrides -datapath").
  (2) else `-datapath X` => data root = **`X/PCSX2x6`** (it APPENDS "PCSX2x6"). (3) else `~/.config/PCSX2x6`.
- THE LANDMINE: a 0-byte `~/Applications/pcsx2x6/portable.ini` forces portable mode and silently voids
  `-datapath`. Move it aside to use -datapath; arcade still works via the explicit `-portable` FLAG.
- Layout used: retail launches `pcsx2x6.AppImage -datapath /home/deck/Applications/pcsx2x6-retail`
  => retail data root `~/Applications/pcsx2x6-retail/PCSX2x6/` (inis/bios/memcards/crosshairs).
  Arcade Namco keeps `-portable` => `~/Applications/pcsx2x6/PCSX2x6/`. Distinct router key `ps2guncon`
  (launchers) points the binder's config_file at the retail ini so arcade pads are never touched.
- MEMORY CARDS: NO code port needed. The fork's pcsx2/SIO/Memcard Save/Create/Open is byte-identical to
  stock github.com/pcsx2/pcsx2 (direct diff 2026-07-01). The arcade "dongle" is a formatted 8MB .ps2 in
  Slot1; arcade boot persists it into the shared base config (VMManager.cpp:1358/1370), so a retail game
  launched after arcade inherited the dongle in Slot1 ("no card"). Fix = the datapath split + retail
  [MemoryCards] Slot1_Filename=Mcd001.ps2. Card auto-creates UNFORMATTED on first launch; format once via
  the PS2 BIOS Memory Card browser (or in-game) then saves persist.

## pcsx2x6 fork RELEASE process (mmadalone/pcsx2x6) - learned 2026-07-01
The automated release_cut_new.yml is gated to `github.repository == PS2Homebrew-arcade/pcsx2x6` (upstream),
so on OUR fork (mmadalone/pcsx2x6) releases are MANUAL. gh CLI is NOT installed - use the REST API + the PAT.
- In-app updater (pcsx2-qt/AutoUpdaterDialog.cpp): reads gh_pages/docs/api/<channel>.json (channel = stable
  or nightly; SteamDeck branch builds set stableBuild:true -> "stable"). "Update needed" = STRING compare
  `m_latest_version == BuildVersion::GitTag` (line 545). GitTag = `git tag --points-at HEAD` at BUILD time
  (cmake/Pcsx2Utils.cmake). => the release AppImage MUST be built AFTER the tag exists or GitTag="" and it
  loops forever.
- Correct release steps: (1) merge the feature branch into deck-patches (release branch) + push; (2) create
  + push tag vX.Y.Z on the tip; (3) RE-RUN the deck-patches CI (linux_build_matrix, fetchTags:true) so the
  build's GitTag=vX.Y.Z; (4) download + verify the binary reads vX.Y.Z (AppImage --appimage-extract, then
  grep squashfs-root/usr/bin/pcsx2* for the tag); (5) create the GitHub release (REST: POST /releases, draft
  then upload asset to uploads.github.com then PATCH draft=false), asset name pcsx2x6-SteamDeck-vX.Y.Z-x64
  .AppImage; (6) update gh_pages/docs/api/stable.json AND nightly.json (REST contents API PUT, needs the
  file sha + branch=gh_pages) to {data:[{version,publishedAt,assets:{Linux:[{name,url,size,additionalTags:[]}]}}]}
  - the size MUST match the uploaded asset. v1.0.4 (retail GunCon2) shipped this way; installed build reads
  v1.0.4, size 59320824.
